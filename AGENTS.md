# Pult

A change outside `plugins/pult` and `apps/pult` that adds to the fork updates monore `pult/fork-additions`, the list of everything the fork adds over upstream, in the same change.

Pult is a fork of T3 Code with its own client: the shell at `apps/pult`, on VS Code's workbench, and the server changes it needs in `apps/server`, kept additive so upstream merges stay easy.

This codebase is the **Pult track**'s (monore `pult/about`), beside `../pult-star` (the Stars' generative art, local only). Read monore `pult/rfc-0` (human-written, never edited by agents) before anything else, then `pult/rfc-2`, the current direction. The track's decisions are monore `pult/decisions`; its design principles `pult/taste`. Cross-track conventions live in monore `/ashakirzianov/axis/AGENTS.md` (read with `query`).

## Where code lives

The source of truth is monore `/ashakirzianov/pult/code`, its history `monore log` and `monore blame`; `~/repos/pult` is a checkout of it, and every agent works in a copy of its own (Rules). `github.com/ashakirzianov/pult`, a GitHub fork of upstream, is its one-way mirror, whose `main` takes commits only from `monore mirror`, the remote it publishes to named by `.monoregit` at the root (`pult/decisions`, `one-repo`). Whatever reads git (upstream's tree, the fork's diff against it) is read in `git_clone`, the CLI's own clone of the code that `monore status --json` names in a copy, after `git -C <git_clone> fetch -q --no-tags origin +refs/heads/main:refs/remotes/origin/main` and the same of `upstream` into `refs/remotes/upstream/main` (`monore mirror` leaves `origin/main` at the tip before its push; a clone with no `upstream` remote gets it from the copy's next `monore mirror`, which syncs the clone's remotes from `.monoregit`): read it, and never commit, push or merge in it.

- `apps/pult`: the shell, a Vite page on VS Code's workbench with upstream's thread view built in; its map and its own conventions are `apps/pult/AGENTS.md`. `apps/pult/view` is the app around the thread view, `apps/pult/desktop` the Electron wrapper.
- `apps/web`: upstream's web app, which is also the shell's thread view, built in place by the shell's Vite. Changes to it are ours to make, kept small and local so upstream merges stay easy, and they may change the fork's own web app; one that makes sense only for the shell is a slot or context there. Each is commented with Pult's use; `git -C <git_clone> diff --stat upstream/main...origin/main -- apps/web` lists them.
- `apps/server`: upstream's server with the fork's changes: the plugin loader, the extension contract and its entry (`src/extensionHost.ts`, which extensions import as `@pult/extension-host`), the raw tier Pult's plugin imports by path (`src/pluginHost.ts`; both described in `docs/internals/plugins.md`, the reference extension `examples/plugins/hello`), and the RPCs Pult needs.
- `plugins/pult`: Pult's server plugin, a workspace package compiled into the server and activated at startup (`apps/server/src/plugins/bundled.ts`; the contract is `docs/internals/plugins.md`, Bundled plugins). Upstream's conventions for Effect server code apply there, `docs/upstream/AGENTS.md`. Its `src/host.ts` re-exports the server's raw host entry (`apps/server/src/pluginHost.ts`) by path and its `src/extension.ts` the extension entry (`apps/server/src/extensionHost.ts`); they are its only imports from the server, Effect included. A lint rule holds the rest of `src` to them, and the features moved onto the extension contract (`src/asks/`) to `src/extension.ts` alone.
- `packages/*`: upstream's packages, `contracts`, `client-runtime`, `shared` and the rest; the shell depends on them as `workspace:*`.
- `apps/desktop`, `apps/mobile`, `apps/marketing`, `infra/`: upstream's.
- **Work in `apps/server`, `apps/web` or `packages/` follows upstream's instructions, `docs/upstream/AGENTS.md`** (its conventions, how the server works, dev servers, test data, verifying). It is upstream's root `AGENTS.md` byte for byte, so its links are relative to the repository's root, and where it says "we" it means upstream's maintainers. Where it assumes git (`git worktree add`, `vp run check:changed`, pull requests), Pult's rules below win: a copy, the checks by package, no pull requests. Its `.repos/`, `.claude/skills` and the mobile speech link `apps/mobile/modules/t3-voice-transcription/ios/AppleSpeechEngine.swift` are not in our tree, which monore must be able to hold: `node scripts/sync-reference-repos.ts` fetches the reference repositories into `.repos/` (gitignored), or `git -C <git_clone> show upstream/main:.repos/<path>` reads one file, and `scripts/setup-worktree.ts` makes the two links; a checkout it did not set up makes them with `mkdir -p .claude && ln -s ../.agents/skills .claude/skills` and `ln -s ../../../../../native/apple-speech/AppleSpeechEngine.swift apps/mobile/modules/t3-voice-transcription/ios/AppleSpeechEngine.swift`.

## Rules

- **The patch surface is the loader, the view's hook points, and Pult's own directories.** Upstream is `pingdotgg/t3code`; we merge it regularly. **We offer nothing upstream for now** (`pult/decisions`, `upstream-offers`): an offer is Anton's own, after his review, so agents neither propose one nor prepare one. Outside `apps/pult` and `plugins/pult`, keep every change inside the plugin loader, the extension contract and its entry, the raw tier, their docs and tests, a hook point a plugin or the shell needs (`pult/decisions`, `plugin-reload`: a change to existing server behaviour is a hook point, never a wrap in a plugin), or an RPC Pult needs. Server changes are additive, so T3 Code's own clients keep working with Pult's server, and one that keeps that compatibility goes behind no feature flag: a new optional field needs none, Pult reading its absence from a stock server as the stock behaviour; a flag is only what a server advertises so a client may call a new RPC (`pult/decisions`, `server-compatibility`, `capability-gated-rpcs`).
- **The installed app is this codebase's server, and `~/.t3` is its live data.** The fork keeps upstream's identity, so its build replaces the installed T3 Code app and runs against `~/.t3` with the fleet's threads (`pult/decisions`, `fork-identity`). Hazard 2 below.
- **Plugins and extensions are code the server trusts completely.** Both run in-process with the server's services, with no capabilities or consent, and contribute UI only as data, through the contract's `ui` (UI slots, drawn by Pult's components) (`pult/decisions`, `plugins-in-process`). Pult's own, `plugins/pult`, is compiled into the server, so it changes only with the server's build and is never installed. An installed extension is `<home>/plugins/<name>/` with an `extension.json` (its version, the contract number, the Effect version it built against) beside `main.mjs`; it imports only `@pult/extension-host`, the server bundle's one stable entry, and the loader refuses before importing it a contract number or an Effect it does not serve; it loads at server start and changes only with a restart (`plugin-reload`). When Pult's plugin needs something the raw tier does not expose, re-export the server module from `src/pluginHost.ts` in the commit of the feature that first uses it, or add a hook point, with a test; the extension entry grows the same way, a contract call or an Effect namespace at its first use (`pult/decisions`, `plugin-host-entry`, `extension-contract`).
- **Builds.** `node_modules/.bin/vp` if `vp` is not on PATH; unset `ELECTRON_RUN_AS_NODE` before a desktop build. Finished artifacts stay in the codebase's `release/` (gitignored), built from a changeset landed on `main`, beside the `COMMIT` note `pnpm desktop:package` writes naming it; Anton installs them. A release's tag is made by GitHub's API on the mirror's commit (`apps/pult/AGENTS.md`, Releases). An unsigned macOS build is signed ad hoc, and a build names an update feed, Pult's own, only on `pnpm desktop:package --feed` (`pult/decisions`, `ad-hoc-signing`, `update-feed`).
- Commits are small and semantically scoped, one logical unit each. **Agents land and mirror on their own** (`axis/decisions`, `push-gate`): `monore commit -m "<subject>"`, `monore land`, then `monore mirror` in the same checkout, by whoever lands. The mirror pushes a commit for every changeset landed under the prefix since the last one mirrored, whoever landed it; it publishes, since the repository is public, and deploys nothing. On `mirror-busy`, another run holds this machine's clone: run it again once that one ends. On `mirror-push`, other machines kept pushing or git refused the push: run it again once theirs ends, or act on git's message. A machine with no clone of `origin` in the CLI's cache makes one on its first run, which takes minutes. Never push to GitHub's `main` by hand: the mirror stops at a commit it did not write (`mirror-foreign-commit`). Never commit secrets, tokens, `.env` files or data copied from `~/.t3`.
- **Every agent works in a copy of its own**, a monore checkout of `/ashakirzianov/pult/code`. Pult makes a thread's (`~/.t3/worktrees/pult/copy-<8 hex>`, `pult/decisions`, `monore-copies`), a `delegate_task` child's with `isolation: "worktree"` at its parent's head, and removes one only once nothing in it waits to land; a builder started otherwise (Claude Code's own `isolation: "worktree"` needs git) makes its own with `monore checkout /ashakirzianov/pult/code <dir>`, runs `T3CODE_PROJECT_ROOT=~/repos/pult node scripts/setup-worktree.ts` in it, and removes it once `monore status` shows no edits, no conflict and nothing to land. There are no branches: a copy's unlanded changesets are its branch, and merge-back is `monore land`, rebased by the server. A land that conflicts exits 2 and leaves the copy at `main`'s tip with git-style markers where the sides overlap: resolve them, or take a side of a path whole with `monore resolve --mine <path>` or `--main <path>`, then `monore commit -m "<subject>"`, land again and mirror. `monore goto` moves a copy with no edits and nothing to land to `main`'s tip; a `cp -r` of a checkout is not a copy.
- Tasks live in monore under the Pult track, `pult/tasks/<slug>.task` (its `project-root` is `/ashakirzianov/pult/`), each carrying the frontmatter's `codebase-url` above. A standing note about the code belongs in `docs/` or beside the code, never the tracker; a design, direction or decision, of use without the code, lives in monore under `pult/`.
- Licence: upstream's MIT text stays.

## The ways to hurt yourself

1. **Killing by pattern.** Never `pkill -f`, `pgrep | kill`, or `kill` a PID you found by matching a name, path or copy string. Your own agent process has this copy's path in its argv, and this machine runs other dev servers at once. Kill only a PID you captured at spawn, or the owner of your port after confirming its working directory is your copy.
2. **Writing to the live install.** `~/.t3/userdata` is the live server's database, in use while you work. Never start a server from this codebase against `~/.t3`, never open `~/.t3/userdata` read-write, never reload or edit `~/.t3/plugins` by hand while the fleet runs. Connecting the shell to the live server as a client, with a pairing link, is fine. A dev run uses its checkout's own `.t3` (or `--home-dir`), every monore checkout (its `.monore-checkout` marker) `~/repos/pult` included, and `vp run migrate-dev-db` seeds it from a read-only snapshot. A shell page served by a Vite of `~/repos/pult` runs that checkout's files as they are edited, through HMR: an edit to what the page writes (a Star's folder, the threads) reaches the live data through any such page connected to the live server, mid-edit, so make it in a copy. A dev server's plugin keeps the Stars of its Stars directory, which follows the server's state: `.pult/stars` beside its home (`<copy>/.pult/stars` for a copy's `.t3`, gitignored); it creates, keeps up and puts to sleep only those. So a dev server has Stars of its own. A `--home-dir` directly under `~` other than `~/.t3` (`~/t3-scratch`, say) would share the live `~/.pult/stars`, so the plugin refuses it: it activates as `failed` and the server runs without it. A page reads its Stars from each server's plugin and writes them only through its routes, so a dev page connected to a dev server reaches that server's Stars alone, and shows none where the plugin is not running; it still syncs each Star's folder, a repository of its own, in the Stars directory a server names, those of the live `~/.pult/stars` through the live server, so a page of a copy connected to the live server is a client of the live Stars like any other.
3. **Two copies of the workbench, or of anything the view shares with the shell.** Vite must see one copy of every `@codingame/*` package, and the shell and `apps/web` one copy of React, Effect, the router and the protocol packages: the shell's dependencies it shares with `apps/web` take the catalog or `apps/web`'s ranges, and `resolve.dedupe` in `apps/pult/vite.config.ts` is the belt. A second copy breaks the workbench's singletons, or the view's contexts, in ways that look like anything else.
4. **Electron's identity and environment.** The shell's dev-identity app (`pult-dev`, "Pult (Dev)") never shares `userData`, its Keychain item or its scheme with an installed Pult (`pult`); a run on another dev server gets a `userData` of its own (`apps/pult/AGENTS.md`). An agent's shell may carry `ELECTRON_RUN_AS_NODE=1`, which turns `electron` into a bare Node: the desktop scripts unset it, so launch Electron through them, not by hand.
5. **Baking in origins**, upstream's third: never set `VITE_HTTP_URL` or `VITE_WS_URL` for upstream's web dev (`docs/upstream/AGENTS.md`).

## Running and verifying

- Node 26 and pnpm 12, through `vp`. `vp i` installs; a thread's copy gets it from the `t3.json` setup action (`scripts/setup-worktree.ts`), so wait for `.t3/setup-done` rather than racing it; a copy made by hand runs it itself with `T3CODE_PROJECT_ROOT` set (Rules), since the script finds the main checkout on its own only through git, which a monore copy is not.
- The shell: `apps/pult/AGENTS.md`, Running. The server and upstream's apps: `docs/upstream/AGENTS.md`, Dev servers.
- `vp run typecheck` in the packages you changed, `vp lint` and knip over them; a hook point in `apps/web` is checked by both `apps/web`'s and `apps/pult`'s typecheck. **Do not run repo-wide checks** unless asked. There is no CI of ours yet; upstream's inherited workflows are disabled.

## Upstream merges

One builder, in a copy of its own (Rules), with no edits and nothing to land; one uptake at a time (`pult/decisions`, `upstream-merge-form`). The remote is `upstream` in `.monoregit`; `monore status --json` in the copy gives `git_clone`, this machine's git clone of the code, `head`, the copy's changeset, and while an uptake waits, `uptake.commit`, upstream's commit taken up.

1. **Take it up:** `monore uptake upstream`. Upstream's `main` is merged into the copy as edits, from git's merge base with the mirror's newest commit, by monore's own three-way. The uptake names what it left out and exits 2 on a conflict. Once it has taken something up, note `uptake.commit` (status drops it at the commit) and the previous pin, `git -C <git_clone> merge-base origin/main <uptake.commit>`, for steps 5 and 7. Possible outcomes:
   - `Up to date` or `changes nothing here`: the merge ends there.
   - It may wait, loudly, with one of these codes:
     - `uptake-behind`: run `monore goto`, then take it up again.
     - `uptake-unlanded`: land and mirror first.
     - `uptake-unmirrored`: run `monore mirror` first.
     - `uptake-foreign` (a commit pushed to GitHub's `main` by hand): run `monore uptake origin`, then commit, land and mirror it, tell Beta, and take up upstream again.
   - Stop and tell Beta on any of these: `uptake-merge-bases`, `uptake-unrelated`, or a `left out, symlink` or `left out, gitlink` line (a link upstream added outside what `.monoreignore` names).
   - If it stopped partway, `monore uptake` with no remote finishes it.
   - To abandon the merge, remove the copy.
2. **Resolve the conflicts:** they sit between `<<<<<<< mine` and `>>>>>>> theirs`, in the server's and the view's hook points. You can take one side of a path whole with `monore resolve <path> --mine` or `--theirs`.
   - No rerere and no rename following: a file upstream renamed or deleted that we changed comes as a conflict with their side deleting it. Carry our change over by hand to where upstream moved the file, then take `--theirs` for the old path.
   - `pnpm-lock.yaml` takes `--theirs`; step 3's `vp i` puts our dependencies back.
   - Keep the list of conflicts and how each was resolved, for the commit's body.
3. **Ours and theirs:**
   - Our root `AGENTS.md` stays ours: `monore resolve AGENTS.md --mine` if it conflicted, or `monore show <head> AGENTS.md > AGENTS.md` if it merged clean.
   - `git -C <git_clone> show <uptake.commit>:AGENTS.md > docs/upstream/AGENTS.md`.
   - Then `vp i`; a lockfile it changes goes with the merge.
   - `vp run typecheck` in `apps/pult`, `apps/web`, `apps/server` and `plugins/pult`.
   - The page run against a dev server of the copy (`apps/pult/AGENTS.md`, Running).
   - Fixes inside the merge are expected, and are committed with it.
4. **Review:** a second agent reviews before the land. It reads:
   - the conflict list against both sides (`monore diff <path>` for ours, `git -C <git_clone> show <uptake.commit>:<path>` for theirs);
   - each rename carried over by hand;
   - every edit beyond the conflicts;
   - the left-out lines.
5. **Land:**
   - `monore commit -m "Merge upstream <first 10 of the commit> into main"`, with the conflict list in the body. The commit adds `Git-Parent:` itself, and refuses a message that already holds one.
   - Then a plain `monore land` and `monore mirror`, never `land --merge` (`merge-git-parent`).
   - A land that conflicts with concurrent landings is fixed by a new commit under the merge's own message, which carries the `Git-Parent:` by itself. If the CLI says the fix dropped the uptake's merge, take upstream up again.
   - A rebase that lands the uptake's changeset as nothing (its changes already on the tip) loses its `Git-Parent:` without a word: the check below is what catches it; then take upstream up again.
   - Check: after `git -C <git_clone> fetch -q --no-tags origin +refs/heads/main:refs/remotes/origin/main`, `git -C <git_clone> merge-base --is-ancestor <the commit> origin/main` exits 0. If not, stop and tell Beta.
6. **Workflows:** run `gh workflow list --all -R ashakirzianov/pult`, and disable every active workflow but `pult-release.yml` (`gh workflow disable <name> -R ashakirzianov/pult`), since upstream adds workflows.
7. **Report:** the merger's report names the route files upstream added since the previous pin, `git -C <git_clone> diff --diff-filter=A --name-only <previous pin>..<the commit> -- apps/web/src/routes`.
