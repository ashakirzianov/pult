# Pult

This repo is **Pult**'s shell: VS Code's workbench, vendored through `@codingame/monaco-vscode-api`, in a Vite page centred on threads, with the Pult extension (`../pult-extension`) built in and connected to a T3 Code Extensible server. It runs no server. It is one repo of the **Pult track** (xaxis `pult/about`), beside `../pult-extension`, `../pult-star` (the Stars' generative art, local only) and the fork `../t3code-extensible`. Cross-track conventions live in `../axis/AGENTS.md`.

- Read xaxis `pult/rfc-0` (human-written, never edited by agents) before anything else, then `pult/rfc-2`, the current direction, and the design on `pult/own-shell`. The track's decisions are xaxis `pult/decisions`; its design principles `pult/taste`.
- The history started fresh on 2026-10-23. The previous line, a web client and an Electron shell, is archived as `ashakirzianov/pult-app`; copy from it by hand when something there is wanted (the vendoring script, the icon renderer, the desktop shell).
- Commits are small and semantically scoped, one logical unit each. **Agents push on their own** (`axis/decisions`, `push-gate`): a push publishes, since the repo is public, and deploys nothing. Never commit secrets, tokens, `.env` files or data copied from `~/.t3`.
- Licence: MIT, upstream's text; it stays.

## Glossary

- **user** means Anton, using Pult to direct coding agents. **agent** means a coding agent run inside a T3 Code thread, which may include you.
- **environment** means one running server and the machine, filesystem and state it owns. **project**, **thread**, **turn** are the server's.
- **workbench** means VS Code's, as the vendored package builds it; a **part** is one of its regions (sidebar, editor part, status bar). The **extension** means the Pult extension, run by the workbench's web worker extension host.

## Where code lives

- `src/main.ts` boots, in order: workers, IndexedDB user data, the workspace file, the connection, the thread pane and its commands (selecting, new threads, parking), the left panel, the extension, the workbench into the page, then the status bar sync and the restored thread selection.
- `src/services.ts` lists the service overrides and the Open VSX gallery; `src/configuration.json` is the shell's settings defaults (chrome off but the sidebar's tabs, editor stock); `src/secrets.ts` persists the workbench's secrets, the page's bearer and the extensions' (localStorage in a browser tab, the desktop wrapper's keychain-backed store when `window.pultDesktop` is present); `src/workers.ts` names the web workers; `src/debug.ts` is the `window.pult` console handle.
- `src/pultExtension.ts` registers the extension as a built-in from its checkout, which `vite/pultExtension.ts` serves file by file (`PULT_EXTENSION_DIR`, or `.env`, default `../pult-extension/extension`). The extension pushes its thread model, and the environment's projects, into the page over the main-thread command `pult-shell.threads` (`src/shellBridge.ts` in the extension).
- `src/connection/` is the page's one connection (`pult/decisions`, `connection-owner`): the vendored runtime with the environment as its platform registration (`connection.ts`), the probe, the page's platform and its one socket (`platform.ts`, `socket.ts`, `mux.ts`), `pult-shell.connect` and `pult-shell.disconnect` (`commands.ts`, which the extension's Connect and Disconnect defer to), and `bridge.ts`, which offers the connection to the extension over main-thread commands, gated because any extension can run them: HTTP to a route allowlist only, the socket ticket answered with a stand-in, and only requests, acks and interrupts on the socket; the bearer stays in the workbench's secret storage.
- `src/threads/` is the shell-rendered thread: the editor pane (`pane.tsx`, registered with the workbench's own editor registries), which mounts upstream's thread view in-process on the page's connection, headerless, its tab carrying the header instead (the project's icon drawn by `projectIcon.ts` after upstream's, the title, the project as a description shown always), its files opening as editor tabs (`files.ts`), its diff the extension's changes view (the Source Control view over the selected thread's project, `src/changes/` in the extension, told the selection by `pult.threadSelected` and asked for a change by `pult.showChanges`) and its thread details panel kept closed, its composer the message and send alone, with the thread's settings (model, reasoning, permission mode, attachments, a draft's machine and branch) in a bar across the pane's bottom that the shell build renders (`pult/decisions`, `composer-settings-placement`), all through the view's host, as the extension builds it for the shell (its `webview/shell/`, into `dist/shell/`, resolved as `pult-extension/thread-view` by `vite/pultExtension.ts`, and built against the same `vendor/t3code/COMMIT` or refused), and the store the extension fills (`store.ts`). The same pane mounts a project's draft of a new thread (`DraftInput`, its tab "New Thread" with the project's icon and name): upstream's composer on the draft the view remembers per project in localStorage, or a new one through upstream's new-thread handler; when the server creates the thread the view stays mounted as that thread's and tells the shell (`onDidPromoteDraft`), and a draft the view goes to from a thread (upstream's New thread on branch, send and new) opens as its project's draft (`openDraft`).
- `src/threads/selection.ts` is the selected thread and `pult-shell.selectThread`: a switch saves the editor part as the previous thread's editor working set and applies the next one's, keeping the thread tab leftmost. Settings (`pult-shell.selectSettings`, Cmd+,) is a selection of its own, with its own working set, and closing its last tab goes back to the thread or draft it was selected from; the stock `workbench.action.openSettings` (the Manage menu, the palette, links to a setting) is re-registered on top to select it first. A project's draft is a selection too, one per project with its own working set (`pult-shell.newThread <projectId>`; without a project it runs the extension's `pult.newThread`, the palette's "Pult: New Thread", which picks one, the selected thread's first, and comes back with it; Cmd+N is bound to the latter over New Untitled File); on promotion the draft's tab is replaced in place by the thread's, keeping the editor part and the mounted view, and the thread is selected, the draft's selection and working set gone.
- `src/threads/park.ts` settles, snoozes and pins threads by the extension's `pult.*Thread` commands, given a thread's id: the cards' actions and menu, and the palette's Pult: Settle Thread, Un-settle Thread, Snooze Thread…, Wake Thread, Pin Thread and Unpin Thread on the selected thread, offered by context keys from the pushed features and the thread's shelf (`parking.ts`, with its test, `node --test src/threads/parking.test.ts`). Settling or snoozing the selected thread from the shell moves the selection to the next pinned or active card, wrapping, or with none to `pult-shell.newThread` in its project. The thread view handles upstream's Cmd+Shift+S itself (`thread.settle`, settling or un-settling, in a capture listener on the page's window, ahead of the workbench's keybindings), so the shell binds none, and that settle does not move the selection.
- `src/threads/statusBar.ts` shows the status bar while an editor other than a thread's or draft's tab is active, through `workbench.statusBar.visible` in the in-memory configuration layer, and moves it from the window's bottom to the editor part's, with the grid's own `moveView` on the layout's grid, as the layout moves the panel.
- `src/panel/` is the left panel: VS Code's activity bar on the left (`workbench.activityBar.location` default) switching the sidebar part between Threads, a view container registered with `registerCustomView` holding the React cards (`PanelView.tsx`), first by its order, with Pult's mark (`assets/pult/mark.svg`) as its icon and New Thread (+) in its title; VS Code's stock Explorer, rooted by setting the workspace folders under a scope the toggle in its title flips, the selected thread's root alone or every root of the environment (`explorer.ts`); and VS Code's Source Control, the extension's changes view. A selected draft has a card of its own at the top (`DraftCard.tsx`); the explorer scopes it to its project's root, and the changes view and Back to Parent see no thread. The cards follow the store's order, upstream's shelves: pinned and active flat, then Snoozed and Settled under collapsible headers with their counts (collapsed until opened, remembered in localStorage), Settled showing ten and a page more per click. On hover or keyboard focus a card's status gives way to its actions, as upstream's: the snooze clock (a menu of upstream's presets and Custom…, while the thread can snooze now) and Settle on a pinned or active card, Wake on a snoozed one, Un-settle on a settled one, each while the server has the feature; a right-click opens the workbench's context menu (Pin or Unpin, Settle or Un-settle, Snooze's presets or Wake, New Thread in Project). Subagents have no card: the extension pushes them on no shelf, with their parent and root, and an expanded card lists its lineage's subagents under one collapsible header with their count and, while any works, Working with the longest elapsed time (collapsed until opened, one state for every card), each selecting its own thread, then its row (Explorer, the branch when the server records one, the environment); a provider's native subagent has no run, so the push always reads it idle, and the mounted thread view reports its lineage's activity from its projection through the host (`reportActivity`), which the store lays over the push; a status reads Working with its elapsed time (a subagent's the elapsed time alone), or Waiting while the thread does nothing itself but its run is held by background work (upstream's) or a subagent below it works; while one is selected its root's card is the expanded one, its tab reads "subagent", and "Back to Parent Thread" (`pult-shell.selectParentThread`) sits in the thread tab's title. Collapsing the sidebar is Cmd+B or the palette, and a chevron in the editor's title brings it back (`view.tsx`); Settings is the activity bar's Manage menu, whose stock command the shell routes through its own selection (`src/threads/selection.ts`); Search, Extensions and the extension's own container are unpinned by default, and Threads is a fresh profile's first tab (`src/services.ts`). The title bar never shows: the workbench shows its custom title bar only for the command center, the layout controls, a menu bar or an activity bar at the top or bottom, none of which the shell has.
- `src/style.css` is the page's own styles, and the guard against the thread view's stylesheet: upstream's Tailwind resets the whole page in its base layer, so an unlayered rule of no specificity gives the workbench outside the view the browser's box-sizing back; a workbench part that looks wrong only once a thread has loaded is probably another leak of that reset.
- `src/nativeScroll.ts` lets a shell-rendered element scroll natively: the workbench cancels every wheel event reaching its container (its guard against macOS's back-and-forward swipe; its own scrollers scroll by script), so the thread pane and the panel's cards stop wheel events below it. Any new native scroller in the shell needs the same.
- `src/identity.ts` names Pult; `assets/pult/` holds the brand assets (its README says what is source and what is rendered).
- `desktop/` is the desktop wrapper (`pult/decisions`, `desktop-wrapper`), a workspace package of its own, development only so far (xaxis `pult/shell-electron-wrapper` holds the rest of the design): Electron's main process (`src/main.ts`: one window on the Vite dev server under the dev identity, links and foreign redirects out to the browser, every permission denied but the page's clipboard and fullscreen, the stock menu), a sandboxed preload exposing `window.pultDesktop` (`src/preload.ts`, its type in the page's `src/desktop/api.ts`), the secrets file and the window's state in `userData` (`secretStore.ts`, `windowState.ts`), no title bar on macOS, where the page leaves the traffic lights a strip of its own above the workbench, in the theme's title bar colour, gone in full screen (`TITLE_BAR_INSET` in `src/ipc.ts`, the page's `src/desktop/titleBar.ts`), and `scripts/build.ts`, which bundles main and the preload with esbuild into `dist/main.cjs` and `dist/preload.cjs`.
- `vendor/t3code/` holds the fork's `contracts`, `client-runtime` and `shared` at the commit in `vendor/t3code/PIN` as workspace packages, with the fork's patches and its blocks of `pnpm-workspace.yaml` (`pult/decisions`, `protocol-packages-pinned`). Read them, never edit them, those blocks included: a bump is a new PIN, here and in the extension, then `pnpm vendor:sync` and `pnpm i`, and `pnpm vendor:check` fails on drift.
- `scripts/drive.ts` drives the page in headless Chromium; `scripts/vendor.ts` vendors; `scripts/setup-worktree.ts` is what T3 Code runs in a new worktree (`t3.json`).
- Below the extension API: `@codingame/monaco-vscode-workbench-service-override/common` exports `registerEditorPane`, `registerEditorSerializer`, `registerCustomView` and the workbench's services; `@codingame/monaco-vscode-api/vscode/vs/...` reaches VS Code's own modules. Read them in `node_modules/@codingame`, never patch them. A VS Code bump is one version for every `@codingame/*` package at once, plus `monaco-editor` and `vscode` aliases in `package.json`.

## Running

Node 24 and pnpm. The extension must be built (`pnpm i && pnpm build` in its `extension/`); the shell serves it from there.

- `pnpm i`, then `pnpm dev` (`vp dev`: the fork's override makes Vite+'s core the shell's `vite`), then open http://localhost:5190/ (the port is strict; the dev server's allowed origin names it). The first load pre-bundles the workbench for a minute.
- Connect with Cmd+Shift+P, "Pult: Connect to Environment", and a pairing link or `<server>/#token=<token>`. The **live** server (the installed T3 Code Extensible) hands out a pairing link in its Settings, Connections; it accepts bearer tokens from any origin. A **dev** server is `vp run dev` in the fork checkout with `T3CODE_DEV_ALLOWED_ORIGINS=http://localhost:5190`; a session token that opens files comes from `node apps/server/src/bin.ts auth session issue --ttl 7d --json` run there with `T3CODE_HOME` set to the dev home.
- `window.pult` in the console: `status()`, `connection()`, `threads()`, `selected()`, `tabs()`, `exec(command, ...args)`, `commands(prefix)`, `read(uri)`, `bridgedSockets()`, `restartExtensionHost()`. Headless: `node scripts/drive.ts 'wait:5000' 'eval:pult.status()' 'shot:/tmp/shell.png'`; the steps are listed at the top of the file. A development build connects without a prompt from `eval:pult.exec('pult-shell.connect', '<pairing link>')`.
- `pnpm desktop:dev` opens the page in Electron as "Pult (Dev)": it builds main and the preload, starts the repo's Vite dev server on the page's port when nothing answers there yet (a `pnpm dev` already up is used as it is), and stops what it started when Electron exits. `PULT_DEV_SERVER_URL` names another page, a loopback `http://` URL, served from here too when nobody does, or an `https://` one. View, Reload (Cmd+R) and Toggle Developer Tools are in its menu; `window.pultDesktop` in the console is the preload's API. Its `userData` is `~/Library/Application Support/pult-dev` (`secrets.json`, `window.json`; `pult-dev-<host>-<port>` on another dev server), its key the Keychain item "Pult (Dev) Safe Storage".
- Stop what you started, by the PID you tracked.

## The four ways to hurt yourself

1. **Killing by pattern.** Never `pkill -f`, `pgrep | kill`, or `kill` a PID you found by matching a name, path or worktree string. Your own agent process has this worktree's path in its argv, and this machine runs other dev servers at once. Kill only a PID you captured at spawn.
2. **Writing to the live install.** `~/.t3/userdata` is the live server's database, in use while you work. Never start a server against it, never open it read-write. Connecting the shell to the live server as a client, with a pairing link, is fine: that is what it is for.
3. **Two copies of the workbench.** Vite must see one copy of every `@codingame/*` package: `.npmrc` auto-installs peers, `resolve.dedupe` in `vite.config.ts` pins `vscode`, `react`, `react-dom`, `effect` and the vendored packages (the thread view imports them from the page), and every `@codingame/*` package is at one version. A second copy breaks the workbench's singletons in ways that look like anything else.
4. **Electron's identity and environment.** A dev-identity app (`pult-dev`, "Pult (Dev)" in `src/identity.ts`) never shares `userData`, its Keychain item or its scheme with an installed Pult (`pult`); connecting either to the live server as a client is fine. A window on another dev server (`PULT_DEV_SERVER_URL`) gets a `userData` of its own, `pult-dev-<host>-<port>` (`pult-dev-localhost-5194`), so two runs side by side never share a Chromium profile or a secrets file; a test run removes the one it made, and leaves `pult-dev` alone. An agent's shell may carry `ELECTRON_RUN_AS_NODE=1`, which turns `electron` into a bare Node and breaks the run: the desktop scripts unset it, so launch Electron through them, not by hand.

## Hit every surface

Before calling work done, walk this list and say which entries applied: the command palette and keybindings (a behaviour reachable from the UI is usually also a command); reverse states (a way in needs a way out and a way to see it); the extension's side (what the shell shows comes from the extension's pushes or the connection the shell owns); docs, where a change makes `AGENTS.md` wrong.

## Verifying

- `pnpm typecheck` for the scope you changed; behaviour through `scripts/drive.ts` against a running dev page, or a browser.
- Test meaningful logic or observable behaviour; do not add tests that mirror the implementation. A test that needs a sleep to pass is wrong.
- **Do not run repo-wide checks** unless asked. There is no CI; the lead integrates by review.
- User-visible changes get one pass in a real browser by the primary agent after integrating. Subagents do not launch their own dev servers unless their task says so.

## Code conventions

The track's design principles are xaxis `pult/taste`. Inferred types over annotations; `any` is the enemy. Comments describe how a thing is used, and move when the code moves. The shell's own UI is React in the page; the workbench's parts are configured and registered into, never patched.
