# Plugins and extensions

The server runs two kinds of in-process code, both fully trusted, with no capabilities or consent. A **bundled plugin** is compiled into the server and gets the server's own modules, the raw tier. An **installed extension** is a directory on the server's disk, written against a narrow, numbered contract of schema-defined calls on the server's own Effect, across which only data passes. The decisions behind that shape are in the Plugins and Extensions areas of monore `pult/decisions`. The loader is [`PluginLoader.ts`](../../apps/server/src/plugins/PluginLoader.ts), the contract [`contract.ts`](../../apps/server/src/plugins/contract.ts) and its implementation [`ExtensionContract.ts`](../../apps/server/src/plugins/ExtensionContract.ts), the HTTP surface [`plugins/http.ts`](../../apps/server/src/plugins/http.ts), and the reference extension [`examples/plugins/hello`](../../examples/plugins/hello/main.mjs).

Everything loads once, at startup: the bundled plugins first, then each installed extension. Nothing watches the disk, and a running plugin or extension changes only with a restart. The loader's one function per folder loads one named extension, so an install (the Extensions tab's call, not built) can load a name that is not running at once; replacing a running one is a restart.

## Installed extensions

```
<home>/plugins/<name>/
  extension.json   { "version": "0.3.0", "contract": 1, "effect": "4.1.5" }
  main.mjs
```

`<home>` is the server's base directory (`--base-dir`, `T3CODE_HOME`). Names are single path segments (`[A-Za-z0-9][A-Za-z0-9._-]*`), and a bundled name shadows a folder of the same name. `version` is the extension's own, listed and never interpreted. The loader reads `extension.json` before importing anything and refuses the extension, listing it `refused` with the reason, when:

- the folder has no `extension.json` (a plugin of the retired form, `builds/` with no manifest, is named as such);
- the manifest does not decode, or its `effect` is not `x.y.z`;
- `contract` is not the number this server serves (`CONTRACT`, 1);
- `effect` has another major than the server's Effect, or is newer than it: the caret range, trusting Effect's semver.

A served extension's `main.mjs` exports `activate(host)`, which must return an Effect; the loader runs it in a scope of its own, closed at shutdown or when activation fails. A failed import or activation lists the extension `failed`, and the rest load.

### The contract, version 1

An extension imports only `@pult/extension-host`, which the loader maps to the bundle's entry [`src/extensionHost.ts`](../../apps/server/src/extensionHost.ts) (`dist/extensionHost.mjs`, sharing its chunks with `dist/bin.mjs`) with a `module.registerHooks` resolve hook. The entry re-exports the contract and the Effect namespaces extensions use (`Effect`, `Schema`, `FileSystem`, `Path`, `Tool`, `Toolkit`), grown when a feature first uses one; it exports no server module and neither of Effect's MCP modules, so an extension cannot name a server service. A test in `PluginLoader.test.ts` pins its export names. An addition does not bump the number.

`activate` gets an `ExtensionHost`:

- `name`, and `dataDir`, `<stateDir>/plugins/<name>/`, made before `activate`.
- `tools.register(toolkit, handlers)`: a `Toolkit` of `Tool`s declared with no `dependencies`, each named `<name>_*` and none the server already has (either fails the registration, so an extension never replaces another's tool or a built-in one), a tool with no parameters leaving `parameters` out (`Tool.EmptyParams`; an empty `Schema.Struct` advertises no `type` and fails the registration), and per tool `{ access, handle }`. `access` is `"acts-as-caller"` or `"reads-as-caller"`, upstream's two rules for a tool of the calling thread; `handle(params, caller)` gets the caller as data, `{ thread: { id, projectId, worktreePath, settledAt, archivedAt, deletedAt }, folder, fenced }`, times as ISO strings, `folder` the thread's worktree or its project's root. The registration hides each tool from outside MCP clients, widens its failure with upstream's refusal, wraps its handler in `McpToolAccess.actsAsCaller` or `readsAsCaller`, and builds `toolkitRegistration` in the activation's scope, so upstream's checks run for the extension's calls as for a built-in tool's. Every tool is offered to every thread; a per-thread visibility rule comes with the first extension that scopes. A registered tool stays for the run, even when the activation fails after registering it, so register tools last.
- `threads.get(id)`, the thread as the caller is given it, or null for an id of none; `threads.send({ threadId, key, header?, text | composed })`, queued behind the thread's work under no mode ceiling, its command and message id `<name>:<key>`, so a key sent again sends nothing, `header` a `{ line, caption }` the server names the extension in (`messageHeader.ts`): with `text` the extension's own message, `createdBy: "agent"`, `creationSource: "server"`; with `composed`, what a handled composer's Send handed over, the user's, `createdBy: "user"`, `creationSource: "web"`, its uploads claimed into the thread through `ThreadMessageIntake` and a picked model applied (a picked runtime or interaction mode is a `todo`); an empty key, a header that does not decode (a line that breaks) and an unknown thread fail with `HostCallError`. `threadEvents`, a `Stream` of `{ _tag: "settled" | "unsettled" | "archived" | "deleted", threadId }` and `{ _tag: "run-completed", threadId, messageId }`, `messageId` the run's `userMessageId`, the message it started from (a steer appended to a run, or a restart's or a usage limit's continuation, names another), told for each update of the run while it is completed, so perhaps more than once, from upstream's committed events, live from the subscription on, each subscriber its own. `projects.list()` and `projects.create({ title, workspaceRoot })`, each project `{ id, workspaceRoot, archivedAt }`, a new one's id minted by the server.
- `ui.publish(slot, items)`, `ui.onAction(handle)` and `ui.onSend(handle)`: the page's UI slots, whose shapes are [`extensionUi.ts`](../../packages/contracts/src/extensionUi.ts) in `@t3tools/contracts` (one slot today, `shelf-row`, a row on the thread shelves). A publish replaces the extension's whole list for the slot, an item that does not decode or a key repeated in it failing the call with `HostCallError`; what is published is state, which the page follows on `extensions.subscribeUi` where the server's config says `extensionUi`, and it goes when the activation's scope closes. `onAction` and `onSend` take one handler each, at `activate` (a second fails with `HostCallError`): an item's action reaches the first as `{ slot, key, action, value }` (`extensions.act`, `value` an ISO time for an action with an `instant` input), a handled composer's Send the second as `{ slot, key, message }` (`extensions.send`), answered with `{ thread }`; each refuses with `ActionRefused` or `SendRefused` and its message, which the page shows. The server refuses by name an unknown extension, slot, key or action, a value an action does not take or needs, a send to an item whose composer is not handled, and a missing handler. An action, and a handled reply, may declare `then`, the shelf and status its row takes, its status's time a published one, the click's instant (`{ of: "click" }`) or the action's input's value (`{ of: "input" }`): the page draws the row so at the click and offers it no actions until the extension publishes the row changed, or until a refusal, when it draws the row as published; one with no `then` is pending until it answers. An action or send that declares `then` publishes its row's new state from its handler; the order of that publish and the answer on the socket is not promised. A publish fails with `HostCallError` for a `then` the page cannot draw: the input's time on an action with no input or on a reply, and a reply's `then` beside a `{ thread }` target, whose send no handler answers.

[`examples/plugins/hello`](../../examples/plugins/hello/main.mjs) registers one tool. `pnpm build` in that folder bundles it with `@pult/extension-host` external and writes `dist/hello/extension.json` with the contract number and the Effect version of the server built from this checkout; copy `dist/hello/` to `<home>/plugins/hello/` and restart the server.

### How the contract grows

A call joins the contract in the commit of the first feature that uses it, with a case in `PluginLoader.test.ts`'s fixture extension, and the entry grows the Effect namespaces that feature names; an addition never bumps `CONTRACT`, a change or a removal does. Version 1 grew in this order: `dataDir` and `tools.register` (the contract's build, `hello`); `ui.publish`, `ui.onAction`, `ui.onSend` (UI slots, for asks); `threads.get`, `threads.send`, `projects.list`, `projects.create`, with `DateTime` and `Semaphore` (asks' tools and notices); `threads.send`'s `composed` and `threadEvents`, with `Stream` (asks' replies and rows); `threadEvents`' `run-completed` (asks' unanswered replies). Next, each with its own move: usage limits, schedules, the Stars' core. Pult's own plugin moves feature by feature: a moved feature imports `plugins/pult/src/extension.ts` alone, as an installed extension would, and reaches what has not moved through an in-plugin port (asks reach the Stars through `stars/forAsks.ts`).

## Bundled plugins

A plugin that must change in step with the server ships inside it. [`bundled.ts`](../../apps/server/src/plugins/bundled.ts) lists them by name, each a dynamic import of a workspace package that exports only `activate` (Pult's is `plugins/pult`), and the pack inlines them into the server's bundle. `activate(host)` returns an Effect, run with the server's whole context provided and a scope the loader owns. Its `host` is the raw tier, `context` and `serve` (below), beside `extension`, the `ExtensionHost` an installed extension of its name would get, whose `dataDir` is where Pult's plugin keeps its bookkeeping. An activation that fails lists the plugin `failed`, and the server runs on.

A bundled plugin imports the server's modules by relative path to [`src/pluginHost.ts`](../../apps/server/src/pluginHost.ts), the raw tier, so it needs no resolve hook, and `apps/server`'s typecheck follows that import into it: an upstream merge that breaks what the plugin uses fails there. The raw tier re-exports the Effect namespaces, the MCP modules with the access wrapper (`McpToolAccess`, its thread helpers as `McpThreadAccess`, `toolkitRegistration`, `Tool` and `Toolkit`), `ServerConfig`, the shared `HostProcess` (the user's home), `ThreadManagementService` with `ThreadLaunchService`, its hook point `ThreadLaunchGuard` and `DispatchModeLimit`, `ServerRuntimeStartup`, `ProjectService`, `ServerEnvironment`, the server's `Scheduler` (merged out of the orchestration runtime for plugins), `DesktopAppUpdate` and `HostPowerMonitor` (merged out of the server's runtime dependencies for plugins) with `DesktopTelemetryReceiver` and `ServerSettings`, for install-at-rest, `WorkspaceEntries` with its watch, the server's `ProcessRunner`, and Effect's `Digest`. A feature of Pult's plugin moves onto the contract by importing a by-path re-export of the extension entry instead.

A bundled plugin declares its tools as the built-in toolkits declare theirs: a `Toolkit` of `Tool`s, handlers built with `McpToolAccess.toLayer` from its declarations (`writesThreads`, `startsThreads` and the rest), registered by building `toolkitRegistration(toolkit, handlers)` with `Layer.build` in the activation's scope. The build shares the server's layer memo, so the toolkit lands on the server's own `McpServer`. A tool is replaced by name and never removed within a run, so register tools last. A tool handler that throws reaches the agent as an RPC defect and the server survives, so a plugin fails its tools with a result (`isError`), not a throw. For Claude, plugin and extension tools are pre-approved in non-read-only sandboxes (`mcp__t3-code__*`) and absent from the read-only allow-list.

Pult's registers its MCP tools last in its activation: `pult_star_message`, `pult_star_list`, a read-only list of this server's Stars with the id, name and description of each, for a thread finding whom to message, `pult_star_sleep`, and `pult_usage_limits`, a read-only answer of this server's provider and hub usage limits, each window with a linear even pace and a warning, for an agent pacing its work, which first asks for the providers' and hubs' refresh when any limits are older than five minutes, at most once per five minutes; its `/about` lists `usage-limits` for it.

## Hook points

A hook point is a server service through which a plugin changes existing behaviour, never a wrap of it in the plugin (monore `pult/decisions`, `plugin-reload`); with nothing registered, the server behaves as upstream's.

- **`ThreadLaunchGuard`** ([`ThreadLaunchGuard.ts`](../../apps/server/src/orchestration-v2/ThreadLaunchGuard.ts)): at most one guard, `(input, launch) => Effect`, registered with `register` in the activation's scope and removed when it closes; a second registration while one is held is a defect. `ThreadLaunchService.launch` runs a launch with no receipt through it, every path into it alike (the web client's `launchThread`, `t3_thread_launch`, schedules, workflows, a plugin's own launches), so the guard may run `launch` under a lock of its own or refuse it with a `ThreadLaunchRefusal`. A launch already accepted (a resend, a launch cut short) replays unguarded, and so does one whose command was accepted while the guard held it and then refused. A refusal fails the launch with a `ThreadLaunchError` of operation `guard` whose message is the refusal's, which the web client's `launchThread` and `t3_thread_launch` (as `invalid_request`) pass on. Pult's guard holds a Star's channel to one open conversation (monore `pult/decisions`, `star-channel-launches`).
- **`VcsDriverRegistry.register`** ([`VcsDriverRegistry.ts`](../../apps/server/src/vcs/VcsDriverRegistry.ts)): a VCS kind other than git, `{ kind, marker, driver, workflow }`, registered in the activation's scope and removed when it closes; a second registration while one is held is a defect. `kind` is a literal of the contracts' `VcsDriverKind` that is not upstream's, `monore` alone. Registering and its release drop the detection cache, so a folder read before activation is read again. Detection takes the nearest of the kind's checkout and `.git`: the driver's `detectRepository` finds the checkout's root with no process, `.git` in a folder between the cwd and that root makes it git's, `.git` beside the marker fails, and the disk check watches the marker as it watches `.git` (monore `pult/decisions`, `vcs-detection-nearest`). A handle of a registered kind carries `workflow` ([`VcsWorkflow.ts`](../../apps/server/src/vcs/VcsWorkflow.ts)), which `GitWorkflowService` and `ReviewService` route status, Get latest, commits, conflicts, diffs, history and the worktree calls to. What git is asked around a worktree or a branch they answer themselves, the same for every registered kind: a checkout is on one line, `main`, with no git commits, refs, branches or remote base, so `hasCommit` is false, `currentBranch` is `main`, the branch names are none, the two worktree-base calls are null, and pruning and deleting a branch do nothing. `listRefs` answers as for no repository, and git's other calls (remotes, refs, pull requests) are refused, as for any kind but git. With nothing registered, such a checkout reads as the git repository around it, or as none. Pult's plugin registers the monore kind first in its activation (monore `pult/decisions`, `vcs-driver-seam`).

## HTTP

`GET /api/plugins` (scope `orchestration:read`) is the per-environment list the Extensions tab reads: `{ name, version, kind, status, error, loadedAt }`, `kind` `bundled` or `installed`, `status` `loaded`, `failed` or `refused`, and `error` the reason; a bundled plugin lists the server's version. A bundled plugin serves `/api/plugins/<name>/<path>` with `host.serve`, published once its activation succeeds, the last call winning; those routes need `orchestration:read` for `GET` and `HEAD` and `access:write` for any other method, and the handler receives the session's scopes to gate further.
