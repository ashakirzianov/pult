# Pult

`apps/pult` is **Pult**'s shell: VS Code's workbench, vendored through `@codingame/monaco-vscode-api`, in a Vite page centred on threads, with upstream's thread view (`apps/web`) built in and connected to T3 Code servers, this repository's `apps/server` among them. The page runs no server. The repository's rules, its hazards and its push rule are the root `AGENTS.md`'s; this file is the shell's map. The Pult extension (the `pult-extension` repo) is retired, folded into this page (`pult/shell-absorbs-extension`).

- Read xaxis `pult/rfc-0` (human-written, never edited by agents) before anything else, then `pult/rfc-2`, the current direction, and the design on `pult/own-shell`. The track's decisions are xaxis `pult/decisions`; its design principles `pult/taste`.
- The shell's history started fresh on 2026-10-23 in its own repository, archived as `ashakirzianov-archive/pult-shell`, and continued here under `apps/pult` from 2026-11-04 (`pult/decisions`, `one-repo`). The line before it, a web client and an Electron shell, is archived as `ashakirzianov/pult-app`; copy from it by hand when something there is wanted (the icon renderer, the desktop shell).
- Licence: MIT, upstream's text; it stays.

## Glossary

- **user** means Anton, using Pult to direct coding agents. **agent** means a coding agent run inside a T3 Code thread, which may include you.
- **environment** means one running server and the machine, filesystem and state it owns. **project**, **thread**, **turn** are the server's.
- **workbench** means VS Code's, as the vendored package builds it; a **part** is one of its regions (sidebar, editor part, status bar). An **extension** means any VSIX the workbench runs, in its web worker extension host, from Open VSX; Pult has none of its own.
- **Star** means Pult's durable agent: the user's one continuous conversation with one agent, a project of its own on an environment whose folder holds its record, instructions and memory, its threads the conversation's substrate.

## Running

The repository's toolchain: Node 26, pnpm 12 through `vp` (`node_modules/.bin/vp` if `vp` is not on PATH); nothing needs building first.

- `vp i` at the repository's root (a worktree's setup does it), then `vp dev` in `apps/pult` (the root's override makes Vite+'s core the shell's `vite`), then open http://localhost:5190/. The port is strict, since a server's allowed origins name it; `vp dev --port 5194` serves another. The first load pre-bundles the workbench for a minute.
- Connect with Cmd+Shift+P, "Pult: Connect to Environment", and a pairing link or `<server>/#token=<token>`; each connect adds an environment beside those held, and "Pult: Disconnect" picks the one to drop. The **live** server (the installed app) hands out a pairing link in its Settings, Connections; it accepts bearer tokens from any origin. A **dev** server is `vp run dev:server` at the root, with `T3CODE_DEV_ALLOWED_ORIGINS=http://localhost:5190` (or the page's port) and, for state of its own, `--home-dir <dir>` (in a worktree it defaults to the worktree's `.t3`); a session token that opens files comes from `node apps/server/src/bin.ts auth session issue --base-dir <dir> --ttl 7d --token-only` run in the root. Its server auto-bootstraps a project from `apps/server`, so a fresh dev server already has a project's draft to open.
- `window.pult` in the console: `status()` (each environment's phase and error, each extension's state), `connection()` (every held environment), `threads()`, `stars()`, `selected()`, `tabs()`, `changes()`, `exec(command, ...args)`, `commands(prefix)`, `read(uri)`, `restartExtensionHost()`. Headless: `node scripts/drive.ts 'wait:5000' 'eval:pult.status()' 'shot:/tmp/shell.png'`; the steps are listed at the top of the file. A development build connects without a prompt from `eval:pult.exec('pult-shell.connect', '<pairing link>')`.
- `pnpm desktop:dev` in `apps/pult` opens the page in Electron as "Pult (Dev)" (the first run downloads Electron's binary): it builds main and the preload, starts the shell's Vite dev server on the page's port when nothing answers there yet (a `pnpm dev` already up is used as it is), and stops what it started when Electron exits. `PULT_DEV_SERVER_URL` names another page, a loopback `http://` URL, served from here too when nobody does, or an `https://` one. View, Reload (Cmd+R) and Toggle Developer Tools are in its menu; `window.pultDesktop` in the console is the preload's API. Its `userData` is `~/Library/Application Support/pult-dev` (`secrets.json`, `window.json`; `pult-dev-<host>-<port>` on another dev server), its key the Keychain item "Pult (Dev) Safe Storage".
- Stop what you started, by the PID you tracked. `vp dev` leaves its Vite child listening when killed: spawn it in a process group of its own and kill the group, as `desktop/scripts/dev.ts` does, or kill the port's owner after confirming its working directory is yours.

## The four ways to hurt yourself

1. **Killing by pattern.** Never `pkill -f`, `pgrep | kill`, or `kill` a PID you found by matching a name, path or worktree string. Your own agent process has this worktree's path in its argv, and this machine runs other dev servers at once. Kill only a PID you captured at spawn.
2. **Writing to the live install.** `~/.t3/userdata` is the live server's database, in use while you work. Never start a server against it, never open it read-write. Connecting the shell to the live server as a client, with a pairing link, is fine: that is what it is for.
3. **Two copies of the workbench.** Vite must see one copy of every `@codingame/*` package: pnpm installs peers, `resolve.dedupe` in `vite.config.ts` pins `vscode`, `react`, `react-dom`, `effect`, the router and the protocol packages (the thread view and the shell share one client runtime and one router), and every `@codingame/*` package is at one version. A dependency the shell shares with `apps/web` takes `apps/web`'s range or the catalog, so both resolve to one copy. A second copy breaks the workbench's singletons, or the view's contexts, in ways that look like anything else.
4. **Electron's identity and environment.** A dev-identity app (`pult-dev`, "Pult (Dev)" in `src/identity.ts`) never shares `userData`, its Keychain item or its scheme with an installed Pult (`pult`); connecting either to the live server as a client is fine. A window on another dev server (`PULT_DEV_SERVER_URL`) gets a `userData` of its own, `pult-dev-<host>-<port>` (`pult-dev-localhost-5194`), so two runs side by side never share a Chromium profile or a secrets file; a test run removes the one it made, and leaves `pult-dev` alone. An agent's shell may carry `ELECTRON_RUN_AS_NODE=1`, which turns `electron` into a bare Node and breaks the run: the desktop scripts unset it, so launch Electron through them, not by hand.

- `vp run typecheck` in `apps/pult` (and in `apps/web` when a hook point changed), `vp run test` for the shell's `node --test` suites, `vp lint apps/pult`; behaviour through `scripts/drive.ts` against a running dev page, or a browser.
- Test meaningful logic or observable behaviour; do not add tests that mirror the implementation. A test that needs a sleep to pass is wrong.
- **Do not run repo-wide checks** unless asked. There is no CI; the lead integrates by review.
- User-visible changes get one pass in a real browser by the primary agent after integrating. Subagents do not launch their own dev servers unless their task says so.
- Seeing a change on the live server is welcome, as its client, with care (`scripts/drive.ts`'s profile may hold a connection already): the user's threads are only read and selected, never sent to, settled, snoozed or pinned; test threads go in the "No project" scratch project (`~/.t3/scratch`), titled "Pult probe …", their turns trivial ("reply with OK") on a cheap model; settle or delete what you made when done, and say so in your report; anything server-wide (a project deleted, a setting changed) is asked first. A page connected to an environment that holds no Star creates one in that environment's home (`~/.pult/stars/star` and its project, `src/stars/`), unless Show Star (`pult.star.enabled`) is off in the page's user settings: never point a fresh profile at the live server without meaning to.

## Code conventions

The track's design principles are xaxis `pult/taste`. Inferred types over annotations; `any` is the enemy. Comments describe how a thing is used, and move when the code moves. The shell's own UI is React in the page; the workbench's parts are configured and registered into, never patched.
