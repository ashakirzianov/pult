# Pult

`apps/pult` is **Pult**'s shell: VS Code's workbench, vendored through `@codingame/monaco-vscode-api`, in a Vite page centred on threads, with upstream's thread view (`apps/web`) built in and connected to T3 Code servers, this repository's `apps/server` among them. The page runs no server; Pult.app, upstream's desktop app (`apps/desktop`) with the page as its renderer, runs one beside it (`pult/decisions`, `desktop-wrapper`, `local-server`). The repository's rules, its hazards and its push rule are the root `AGENTS.md`'s; this file is the shell's map. The Pult extension (the `pult-extension` repo) is retired, folded into this page (`pult/shell-absorbs-extension`).

- Read xaxis `pult/rfc-0` (human-written, never edited by agents) before anything else, then `pult/rfc-2`, the current direction, and the design on `pult/own-shell`. The track's decisions are xaxis `pult/decisions`; its design principles `pult/taste`.
- The shell's history started fresh on 2026-10-23 in its own repository, archived as `ashakirzianov-archive/pult-shell`, and continued here under `apps/pult` from 2026-11-04 (`pult/decisions`, `one-repo`). The line before it, a web client and an Electron shell, is archived as `ashakirzianov/pult-app`; copy from it by hand when something there is wanted (the icon renderer, the desktop shell).
- Licence: MIT, upstream's text; it stays.

## Glossary

- **user** means Anton, using Pult to direct coding agents. **agent** means a coding agent run inside a T3 Code thread, which may include you.
- **environment** means one running server and the machine, filesystem and state it owns. **project**, **thread**, **turn** are the server's.
- **workbench** means VS Code's, as the vendored package builds it; a **part** is one of its regions (sidebar, editor part, status bar). An **extension** means any VSIX the workbench runs, in its web worker extension host, from Open VSX; Pult has none of its own.
- **Star** means Pult's durable agent: the user's one continuous conversation with one agent, a project of its own on an environment whose folder holds its record, instructions and memory, its threads the conversation's substrate.

its more menu's Close browser session the shell's `onEndSession`), the shell's tabs being `src/preview/`. `stubs.ts` maps the upstream modules our files replace. `vite.config.ts` builds it as the fork builds its web app: the stubs, Tailwind (`view/tailwind.css` adds `apps/web/src` to its sources, since it looks under the page's root alone), the React Compiler (for `apps/web/src` and `view/` only), the `~` alias to `../web/src`, the fork's build-time env, and upstream's Dev stage left out of the development build. `effect-tsgo tsrs -b` (the typecheck script) checks `view/` and `apps/web/src` but its tests as a project of its own with `apps/web`'s settings (`view/tsconfig.json`, checked against `apps/web`'s router), which the page's program reads through its declarations.
- The protocol packages are the repository's own: `@t3tools/contracts`, `client-runtime`, `shared` and `provider-core` as `workspace:*` dependencies, at whatever commit the repository is at (`pult/decisions`, `protocol-packages`); the shell follows upstream only through the repository's merges of it. `apps/web`'s own dependencies resolve from `apps/web/node_modules`, so the shell lists only what its own files import.
- `scripts/drive.ts` drives the page in headless Chromium. A new worktree is set up by the repository's `t3.json` action.
- Below the extension API: `@codingame/monaco-vscode-workbench-service-override/common` exports `registerEditorPane`, `registerEditorSerializer`, `registerCustomView` and the workbench's services; `@codingame/monaco-vscode-api/vscode/vs/...` reaches VS Code's own modules. Read them in `node_modules/@codingame`, never patch them. A VS Code bump is one version for every `@codingame/*` package at once, plus `monaco-editor` and `vscode` aliases in `package.json`.

## Running

The repository's toolchain: Node 26, pnpm 12 through `vp` (`node_modules/.bin/vp` if `vp` is not on PATH); nothing needs building first.

- `vp i` at the repository's root (a worktree's setup does it), then `vp dev` in `apps/pult` (the root's override makes Vite+'s core the shell's `vite`), then open http://localhost:5190/. The port is strict, since a server's allowed origins name it; `vp dev --port 5194` serves another. The first load pre-bundles the workbench for a minute.
- Connect with Cmd+Shift+P, "Pult: Connect to Environment", and a pairing link or `<server>/#token=<token>`; each connect adds an environment beside those held, and "Pult: Disconnect" picks the one to drop. The **live** server (the installed app) hands out a pairing link in its Settings, Connections; it accepts bearer tokens from any origin. A **dev** server is `vp run dev:server` at the root, with `T3CODE_DEV_ALLOWED_ORIGINS=http://localhost:5190` (or the page's port) and, for state of its own, `--home-dir <dir>` (in a worktree it defaults to the worktree's `.t3`); a session token that opens files comes from `node apps/server/src/bin.ts auth session issue --base-dir <dir> --ttl 7d --token-only` run in the root. Its server auto-bootstraps a project from `apps/server`, so a fresh dev server already has a project's draft to open. A dev server's Stars are its own: its plugin serves those of `.pult/stars` beside its home (`<worktree>/.pult/stars` for a worktree's `.t3`, gitignored), so a page connected to it creates a disposable Star there and syncs that directory, never the real Star; the seeded `.t3` (`vp run migrate-dev-db`) knows the real Star's project, which the plugin lists as hidden and serves as no Star. A `--home-dir` directly under `~` other than `~/.t3` would share the live `~/.pult/stars`, so the plugin refuses it and that server shows no Star (root `AGENTS.md`, hazard 2).
- `window.pult` in the console: `status()` (each environment's phase and error, each extension's state), `connection()` (every held environment), `threads()`, `stars()`, `selected()`, `tabs()`, `changes()`, `exec(command, ...args)`, `commands(prefix)`, `read(uri)`, `restartExtensionHost()`. Headless: `node scripts/drive.ts 'wait:5000' 'eval:pult.status()' 'shot:/tmp/shell.png'`; the steps are listed at the top of the file. A development build connects without a prompt from `eval:pult.exec('pult-shell.connect', '<pairing link>')`.
- `pnpm desktop:dev` in `apps/pult` opens the page in Electron as "Pult (Dev)" (the first run downloads Electron's binary): it builds main and the preload, starts the shell's Vite dev server on the page's port when nothing answers there yet (a `pnpm dev` already up is used as it is), and stops what it started when Electron exits. `PULT_DEV_SERVER_URL` names another page, a loopback `http://` URL, served from here too when nobody does, or an `https://` one. View, Reload (Cmd+R) and Toggle Developer Tools are in its menu; `window.pultDesktop` in the console is the preload's API. Its `userData` is `~/Library/Application Support/pult-dev` (`secrets.json`, `window.json`; `pult-dev-<host>-<port>` on another dev server), its key the Keychain item "Pult (Dev) Safe Storage".
- `pnpm desktop:host` in `apps/pult` runs Pult.app in development as "Pult Host (Dev)" (`desktop/scripts/host-dev.ts`): it builds upstream's main and preload under Pult's brand, starts the page's Vite on `PULT_PAGE_PORT` (5194) and Electron on it, its local server the built `apps/server` (`vp pack` there first; `vp run migrate-dev-db` at the root seeds the checkout's `.t3`) on `T3CODE_PORT` (3794) with its home in `T3CODE_HOME` (the checkout's `.t3`); it refuses port 3773 and `~/.t3`. `--local-server=on|off` writes upstream's setting into `<home>/userdata/desktop-settings.json` first; `--devtools` opens DevTools detached, as upstream's development does; arguments after `--` go to Electron (`--remote-debugging-port=9334` to drive it). Its `userData` is `~/Library/Application Support/pult-host-dev`, its key the Keychain item "Pult Host Dev Safe Storage", its scheme `pult-host-dev`. The app's relaunch (exit 75) starts Electron again; Ctrl+C stops both process groups. Its local server's Stars are those of `.pult/stars` beside `T3CODE_HOME` (the checkout's `.pult/stars`), its own, where a page with Show Star on creates a disposable Star; the seeded `.t3` (`vp run migrate-dev-db`) knows the real Star's project, which that server's plugin hides and serves as no Star. Limits: Vite's HMR does not reach the page through the scheme, so reload (Cmd+R) after a change; `pnpm desktop:dev` keeps HMR, which is why the wrapper stays the client-only launcher.
- `pnpm desktop:package` in `apps/pult` builds Pult.app (`desktop/scripts/package.ts`): the page's `vp run build`, then upstream's `scripts/build-desktop-artifact.ts` with `T3CODE_DESKTOP_BRAND=apps/pult/desktop/src/brand.ts`, by default a dmg and its zip for this Mac's arch into the root's `release/`, then a `COMMIT` note beside them naming the commit built (`dirty` after it when the tree had uncommitted changes); other arguments pass through (`--output-dir`, `--target dir`, `--signed`). `--app-version <x.y.z>` sets the version of the app bundle alone (its `Info.plist`, `latest-mac.yml`, the artifact names; the artifact script's `--app-version`), Pult.app's own line, while the server and the packages keep upstream's and no manifest is rewritten; without it the bundle carries upstream's. The brand names the app and its icons: the production app is "Pult", no stage label (`productionStageLabel`), its icons `assets/pult/prod/`, a development run's `assets/pult/dev/` in the dock (`icons`). Unsigned it is signed ad hoc; `--signed` signs with the Developer ID under hardened runtime (`CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_API_*`), with no passkey entitlements when no provisioning profile is configured (`ad-hoc-signing`). It names an update feed only on `--feed`, and then `ashakirzianov/pult` (`UPDATE_FEED_REPOSITORY` in `src/brand.ts`); the script strips `GITHUB_REPOSITORY` and `T3CODE_DESKTOP_UPDATE_REPOSITORY` from the artifact script's environment, so a build without `--feed` ships no `app-update.yml` (`update-feed`). The packaged app is `com.pult.pult`, scheme `pult`, `userData` `pult`, Keychain item "pult Safe Storage", and its server takes upstream's home, port and CLI (`~/.t3`, 3773, the `t3` shim): never launch it while the installed app's server runs, and never from an agent.
- Pult.app's known gaps: upstream's user-facing strings inside dialogs, the macOS usage descriptions (`NSCameraUsageDescription` and the rest) and the dmg's background are T3 Code's; the hosted web app's Codex sign-in hands off to `t3code://auth/codex` (`packages/shared/src/codexAuthHandoff.ts`), which reaches T3 Code, not Pult.app, so sign in through the server's own flow; with the local server off, Pult.app and a stock T3 Code app on the same machine share `~/.t3/userdata/desktop-settings.json`, so one's off is the other's (`pult/issues/separate-identity`); the macOS shell environment for a Finder launch is upstream's import (`DesktopShellEnvironment.ts`), untested under Pult's brand; the packaged menu and Linux and Windows builds are untested.
- **Releases** (`pult/issues/release-feed`): an annotated tag `pult-v<x.y.z>` on a commit of `main`, pushed (`git tag -a pult-v0.0.2 -m "<the release notes>" && git push origin pult-v0.0.2`), runs `.github/workflows/pult-release.yml` on a GitHub macOS arm64 runner: `desktop/scripts/package.ts --app-version <x.y.z> --feed --signed`, then checks that the dmg's app names the feed `ashakirzianov/pult` and carries the tag's version, and that it verifies under `codesign`, Gatekeeper and `stapler`, then `desktop/scripts/smoke.ts` launches it from the dmg against upstream's fixture database and waits for `html[data-pult-local="connected"]` (the page's own server connected, `src/connection/index.ts`) and the fixture's thread in the panel, and only then publishes the GitHub Release "Pult <x.y.z>" (dmg, zip, both blockmaps, `latest-mac.yml`, notes from the tag's annotation, marked latest). A signed build needs the repository secrets `CSC_LINK` (the Developer ID Application certificate, base64 `.p12`), `CSC_KEY_PASSWORD`, `APPLE_API_KEY` (the App Store Connect key's `.p8` contents), `APPLE_API_KEY_ID` and `APPLE_API_ISSUER`, and fails at its first step without one. A dry run builds and smoke-tests a commit without publishing: `gh workflow run pult-release.yml -R ashakirzianov/pult -f version=<x.y.z> -f publish=false` (`-f signed=false` without the secrets); with `publish=true` it releases the existing tag `pult-v<x.y.z>`, signed only. A release is the tag push alone: its run checks and smoke-tests the build before it publishes, and a dry run's build is not reused, so a dry run first only costs another slow macOS build; dispatch one for a change to the build or the workflow, and if a tag's run fails, nothing is published, and the tag is deleted and cut again after the fix.
- Stop what you started, by the PID you tracked. `vp dev` leaves its Vite child listening when killed: spawn it in a process group of its own and kill the group, as `desktop/scripts/dev.ts` does, or kill the port's owner after confirming its working directory is yours.

## The four ways to hurt yourself

1. **Killing by pattern.** Never `pkill -f`, `pgrep | kill`, or `kill` a PID you found by matching a name, path or worktree string. Your own agent process has this worktree's path in its argv, and this machine runs other dev servers at once. Kill only a PID you captured at spawn.
2. **Writing to the live install.** `~/.t3/userdata` is the live server's database, in use while you work. Never start a server against it, never open it read-write. Connecting the shell to the live server as a client, with a pairing link, is fine: that is what it is for.
3. **Two copies of the workbench.** Vite must see one copy of every `@codingame/*` package: pnpm installs peers, `resolve.dedupe` in `vite.config.ts` pins `vscode`, `react`, `react-dom`, `effect`, the router and the protocol packages (the thread view and the shell share one client runtime and one router), and every `@codingame/*` package is at one version. A dependency the shell shares with `apps/web` takes `apps/web`'s range or the catalog, so both resolve to one copy. A second copy breaks the workbench's singletons, or the view's contexts, in ways that look like anything else.
4. **Electron's identity and environment.** A dev-identity app (`pult-dev`, "Pult (Dev)" in `src/identity.ts`, and Pult.app's development run, `pult-host-dev`, "Pult Host (Dev)" in `desktop/src/brand.ts`) never shares `userData`, its Keychain item or its scheme with an installed Pult (`pult`) or with the other; connecting either to the live server as a client is fine. A window on another dev server (`PULT_DEV_SERVER_URL`) gets a `userData` of its own, `pult-dev-<host>-<port>` (`pult-dev-localhost-5194`), so two runs side by side never share a Chromium profile or a secrets file; a test run removes the one it made, and leaves `pult-dev` alone. An agent's shell may carry `ELECTRON_RUN_AS_NODE=1`, which turns `electron` into a bare Node and breaks the run: the desktop scripts unset it, so launch Electron through them, not by hand.

## Verifying

- `vp run typecheck` in `apps/pult` (and in `apps/web` when a hook point changed), `vp run test` for the shell's `node --test` suites (`src/` and `view/`), `vp lint apps/pult`; behaviour through `scripts/drive.ts` against a running dev page, or a browser.
- Test meaningful logic or observable behaviour; do not add tests that mirror the implementation. A test that needs a sleep to pass is wrong.
- **Do not run repo-wide checks** unless asked. There is no CI; the lead integrates by review.
- User-visible changes get one pass in a real browser by the primary agent after integrating. Subagents do not launch their own dev servers unless their task says so.
- Seeing a change on the live server is welcome, as its client, with care (`scripts/drive.ts`'s profile may hold a connection already): the user's threads are only read and selected, never sent to, settled, snoozed or pinned; test threads go in the "No project" scratch project (`~/.t3/scratch`), titled "Pult probe …", their turns trivial ("reply with OK") on a cheap model; settle or delete what you made when done, and say so in your report; anything server-wide (a project deleted, a setting changed) is asked first. A page connected to environments that hold no Star asks the first whose Pult plugin serves Stars for one (`~/.pult/stars/star` and its project on the live server, `src/stars/`), unless Show Star (`pult.star.enabled`) is off in the page's user settings: never point a fresh profile at the live server without meaning to.

## Code conventions

The track's design principles are xaxis `pult/taste`. Inferred types over annotations; `any` is the enemy. Comments describe how a thing is used, and move when the code moves. The shell's own UI is React in the page; the workbench's parts are configured and registered into, never patched.
